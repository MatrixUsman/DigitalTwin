# Repeatable research playbook

Version 1 — 2026-10-16. This is the living procedure for water, manufacturing, and smart grids. Update it as we learn from actual work. The [roadmap](RESEARCH_ROADMAP.md) explains the lifecycle; this file explains how to repeat each step. Each project's `docs/WORK_LOG.md` records what actually happened; its `STATUS.md` is the current handoff.

Reuse the process while independently checking each sector's papers, data, assumptions, and contribution. The existence of this checklist does not authorize downloads, installations, experiments, external messages, or publication beyond the user's current instructions.

Apply the confirmed [publication, writing and title standards](PUBLICATION_STANDARDS.md) across all three sectors. Leading-journal ambitions guide the rigor of the study; publication and professional-use claims must remain supported by actual evidence.

## Start and finish every session

1. Select the active project and bounded task from the user's instruction or its recorded next step. Read root and project `AGENTS.md`, its brief, status, and latest work-log entries.
2. Check prerequisites in the relevant step below. Continue authorized independent work if an external dependency is pending; record the blocker without declaring the whole step finished.
3. Execute only the scoped work. Save source evidence and artifacts in the active project. For commands needed to reproduce a result, record the exact working directory, command, configuration, versions, and output location. Mark proposed commands as **not run**.
4. Append a dated entry using the template below. Record unsuccessful attempts and protocol changes as well as successes. Keep access credentials, signed download links, restricted data, and private identifiers out of shared documentation.
5. Update the project's `STATUS.md`, then update this playbook only when there is a generalizable procedure or lesson. A change to shared workflow belongs in the [root work log](WORK_LOG.md).

## Lessons already established

- Teach core concepts before detailed model implementation using one explicitly synthetic sector example: physical process → expected measurement → residual/score → threshold → alarm → separate evaluation. Distinguish baseline/ablation, data roles, state/parameter/threshold updates, and hidden labels versus available observations. Use a small worked confusion matrix and explain why test-driven choices bias evaluation. Save assistant teaching material separately from the researcher's own unanswered note; require their actual explanation before recording understanding or reading. Water's [Step 0 lesson](../water/docs/RESEARCH_BASICS_LESSON.md) is a prepared teaching example, not a validated learning outcome. Adapt the example and verify each other sector's physical assumptions independently.
- Dataset names alone do not establish comparability. Resolve the exact release, preprocessing, time ordering, labels, and accessible inputs before selecting the final comparison.
- Audit checkpoint selection, threshold search, and final metric reporting separately. Water's CAROTS audit found different test-based best-F1 paths; changing one does not establish a leak-free evaluation. See [water evidence](../water/docs/literature/CAROTS_AND_INFORMATION_THEORETIC.md).
- A public listing or repository is a lead until authorization, contents, provenance, and usability are checked. A simulator, bus case, architecture framework, or fault record is not automatically an attack dataset or runnable detector.
- Keep setup checks, synthetic tests, measured benchmark results, and published paper scores explicitly distinct. Never mark a sibling project's stage complete because water completed a similar step.
- Select per-sector decisions explicitly: water requires both SWaT and WADI; manufacturing needs production/run semantics; grids need electrical/topology and scenario semantics. These are different inputs to the same audit process.
- Separate baseline implementation/development from final benchmark scoring. Freeze the proposed method, all variants and analysis before inspecting final held-out outcomes. Designing an improvement around baseline test failures makes later results on the same attacks exploratory; a different seed is not independent confirmation. Water's [detailed roadmap](../water/docs/RESEARCH_ROADMAP.md) is a planning example, not evidence that its future steps have been executed.
- Select learning papers separately from execution-ready baselines. Use evidence-based admission rules and complementary scientific roles, rather than filling a fixed quota or choosing the largest published score. Water's [selection criteria](../water/docs/BASELINE_SELECTION_CRITERIA.md) provide a reusable example; substitute each sector's own task, data pair and trusted-input requirements, and verify all evidence independently.
- Preserve a dated search record with exact queries, primary-source locators, exclusions and unresolved facts. Pin code when making detailed implementation claims; distinguish author text, direct code observations, third-party issue reports and our inferences. Failed browser PDF retrieval can sometimes be resolved by reading an authorized public manuscript in memory; record its hash and retrieval procedure, then append a correction to the earlier access limitation. Water's [expanded audit](../water/docs/literature/EXPANDED_SEARCH_2026-10-16.md) demonstrates the source-audit procedure, not reproducibility of its methods.
- Build one resource pack per selected method after collection is authorized. Inventory publisher/preprint versions, code license and pinned tree, supplements, figure/table sources, references, models, scores and logs separately. Download only identified relevant files; a full repository archive may silently include unrelated or restricted datasets. Preserve original bytes, URL/version/time/size/hash and extraction provenance, keep artifacts ignored, and inspect downloads without executing code or deserializing checkpoints. A public TeX archive is manuscript source, not model code; a component checkpoint is not necessarily the detector checkpoint. Record unavailable resources and release/access blockers instead of calling the pack complete. Water's [collection](../water/baselines/README.md) and WATER-007 demonstrate this bounded procedure with public artifacts; they do not demonstrate dataset acquisition or model reproduction. Reapply the procedure independently to manufacturing/grids using their own providers and releases.
- Audit resource packs on separate axes: publication identity/status, file integrity, accuracy of our extraction, internal scientific consistency, reference identity/support and execution readiness. Check original plot curves against captions/decision rules; recompute table arithmetic and formulas under their stated assumptions; trace selection, alignment and checkpoint paths without running untrusted code. Inventory rendered references separately from unused bibliography records, compare DOI/title/authors/venue against primary metadata, and inspect consequential citation support in the actual source. Correct our notes while preserving originals. A genuine article, matching hash, valid syntax or resolved DOI is not proof of correct experiments; access failure is not proof of fabrication. Water's [verification report](../water/docs/BASELINE_VERIFICATION_REPORT.md) and WATER-008 demonstrate this audit with explicit coverage and limits. Carry the procedure, not its verdicts, to the other sectors.
- Study one method from input to alarm using its versioned manuscript and pinned code. Map data preparation, model fitting, objective, checkpoint selection, scores, calibration and reporting to actual functions and line ranges. Trace tensor dimensions, indexing, reductions and configuration overrides; a matching class name does not prove equation fidelity. With no matched code, record an implementation contract of inputs, outputs, retained state and unknown choices, explicitly labelled conceptual. Separate the paper specification, observed code and our proposed corrections. Water's [Stage 2 guide](../water/docs/PAPER_STUDY_GUIDE.md) demonstrates source study and mapping, not execution. Preserve original bytes, link reproducibility questions and leave human-reading status unconfirmed until the researcher supplies a scope-specific account.
- For adaptive twins, inventory state assimilation, parameter learning, normal-reference/threshold calibration and alarm reporting separately, including normalization and score-fusion updates. Check when residuals are formed, when updates are committed and which history is admitted. An alarm gate does not necessarily protect learning; update order alone does not prove contamination or a novel defense. Water's [mechanism comparison](../water/docs/MECHANISM_COMPARISON.md) is an audited source comparison with missing details retained, not an established improvement. Recheck each sector's estimator, trusted inputs and attack capabilities independently.
- For authorized dataset applications, prepare and verify concrete identity fields and current terms before submission. Record explicit consent where required and submit once; retain private identifiers and receipt details in ignored local storage. Separate website confirmation, email delivery, provider approval, download authorization and byte receipt. Record timezone differences without inventing an exact server timestamp. Water's [request record](../water/docs/DATASET_REQUEST_PREPARATION.md) documents a confirmed submission only; other users/projects need their own authorization and do not inherit access.
- Before claiming an exact dataset release, separate provider collection/revision labels, baseline loader expectations, mirror-advertised metadata and our received-byte measurements. Inventory bounded local storage without following unapproved external symlinks; preserve unknowns as null with a status, not copied paper counts or empty-file digests. Check timezone/date parsing, chronology, missing-row gaps, schema and label/event reconciliation before dropping metadata or building windows. Keep original and derivative hashes separate, and retain catalogue conflicts until documentary evidence resolves them. Water's [Stage 3 audit](../water/docs/DATASET_IDENTITY_AUDIT.md) demonstrates source verification, an empty local inventory and a receipt contract; actual-file profiling remains unexecuted. Apply the same separation to each sector independently, with its own received data and permissions.

## Work-log entry template

Copy this into the active project's `docs/WORK_LOG.md` after substantive work. Use sequential project-specific entry IDs. Use the root log for shared changes. Do not add placeholders as if they were completed entries.

```text
### YYYY-MM-DD — PROJECT-NNN — Bounded task
Record type: contemporaneous / retrospective summary (identify source)
Scope and authorization:
Prerequisites and starting state:
Actions actually completed:
Evidence/artifacts (paths, source URLs and exact versions as applicable):
Commands and working directories (or not applicable / unavailable):
Checks and observed outcomes:
Failures, unresolved facts and decisions:
Reusable lesson / playbook change (or none):
Run state: none / synthetic software check / pilot / benchmark (run-record path)
Next bounded action and prerequisites:
```

For experiments, link the detailed run record required by `AGENTS.md`; this short session entry does not replace it. Preserve failed runs. Append a correction if an earlier entry proves wrong.
