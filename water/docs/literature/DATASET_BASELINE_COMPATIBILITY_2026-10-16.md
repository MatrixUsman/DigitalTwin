# Dataset compatibility across the three water learning papers

Audit date: **16 October 2026**. This is a static comparison of the collected primary manuscripts and the pinned CAROTS author code. It records what the authors specify, what the code would do, and what remains unknown. No benchmark file was opened, no author code was run and no dataset hash was measured in this subtask. Provider approval and raw-data receipt remain pending. The parent Stage 3 audit records the workspace inventory and provider release evidence separately.

**No exact three-paper release match can currently be established.** CAROTS provides concrete loader paths; IT-DT and the ensemble do not provide enough file-level provenance to match them. A future common-release rerun can be scientifically useful, but it would not establish that we reproduced all three authors' original data pipelines.

There is **no timestamp parsing, date-order specification, sorting, duplicate-time check, gap detection or episode reset** in these water loading branches. Removing timestamp fields and assuming rows are contiguous does not preserve temporal evidence. For WADI, row deletion can make nonadjacent moments appear adjacent to a downsampler or ten-row window. The source does not check that train and test column names/order match, despite setting `var_names` from training.

The code contains no explicit first-six-hour or multi-day startup filter; a required exclusion may already have occurred in an expected provider revision. That relationship remains unresolved. Preserve provider originals, then record any documented revision exclusion separately from our own cleaning.

## IT-DT: information still needed for a faithful data pipeline

The [preprint](https://arxiv.org/html/2603.01621v1) provides normal durations and a residual-window rule but no loading code. It identifies state-space matrices from seven normal SWaT days and fourteen normal WADI days; its offline threshold uses an attack-free validation set. The exact nonoverlapping allocation of those normal records between fitting and calibration is not specified. The separate validation-F1/window-selection passage needs its own label and split provenance; this is an unresolved ambiguity, not proof of test leakage.

Before a same-release implementation claim, obtain or explicitly replace:

1. Provider revision, original filenames, archive/member hashes and original versus retained row counts.
2. Ordered feature channels and the separate observed-output `y` versus control-input `u` mapping. The stated WADI measurement count 127 cannot be silently replaced with 123, nor can every actuator reading be assumed trustworthy.
3. Timestamp grammar, timezone interpretation, input/output timing and the exact sample interval used during system identification and filtering.
4. Startup removal, gaps/resets, missing values, scaling, duplicated observations and any resampling rule.
5. Exact normal fitting/development/calibration and final attack-evaluation boundaries.
6. Label encoding, event interval endpoint semantics and the release-specific mapping for “Attack #41.” Its identity and duration must come from the corresponding annotations, not the example figure.

The reported window `W=60` means sixty residual observations in the algorithm. It is not evidence of a sixty-second window without known cadence and gap handling. Similarly, the reported fractional detection delay does not identify the raw timestamp resolution. No authentic raw-file checksum, parsed time range or release-specific label dictionary can be recovered from the manuscript alone.

## Ensemble: reported splits cannot yet be reproduced

The [setup passage](https://pmc.ncbi.nlm.nih.gov/articles/PMC13402577/#Sec14) allocates SWaT days 1–7 to training, day 8 to normal-only validation and days 9–11 to test with all 41 attacks. The [official SWaT description](https://www.sutd.edu.sg/itrust/itrust-labs/datasets/dataset-characteristics/swat/) describes seven normal days followed by four attack-containing days for the December 2015 collection. An omitted filtering/resegmentation step or another release might explain the difference, but no such mapping is supplied. Day numbers without dates and original row IDs cannot resolve it.

The paper also describes 10 Hz synchronization and a 50-sample window interpreted as five seconds. Its total of 946,722 SWaT samples over eleven days would average approximately 0.996 samples/second if those days were fully covered; eleven complete days at 10 Hz would have 9,504,000 samples. This arithmetic is a **coverage/cadence reconciliation question**, not proof about the actual acquisition frequency. Missing samples, retained subsets and resampling could matter, but their records are absent. Do not interpolate a provider file to 10 Hz merely to reproduce the prose's time units.

WADI's day-based split—training 1–11, validation 12, testing 13–16—also needs original timestamp boundaries, missingness decisions and a release-matched attack list. The manuscript's 123-feature count does not establish equality with CAROTS's independently cleaned input columns. Neither the table nor “15 attack types” supplies the exact event IDs, start/end inclusivity or per-row binary labels needed for evaluation.

Table 1's training-statistic min–max normalization and the separate adaptive EWMA/imputation descriptions are insufficient to reconstruct ordered preprocessing. We need the fitted-state source, update timing, missing-value policy, future-information restrictions and sample-to-score map. These are particularly important for latency and detection-delay claims. No raw-file manifest or author preprocessing implementation is available in the verified collection.

## Common future contract, not a freeze or a claimed reproduction

CAROTS's expected filenames are useful acquisition targets, subject to provider approval and actual delivery. Do not declare them the shared experimental release until both their provenance and the necessary comparator deviations are documented. Maintain one water-project raw store and one release manifest; baseline folders should reference it rather than contain divergent raw copies.

After authorized receipt, the common contract should retain:

- **Byte identity:** original download/archive/member name, byte length and SHA-256 measured before transformations. Keep archive and extracted-member hashes distinct. A locally computed hash verifies stable bytes, not provider origin without the associated delivery record.
- **Row identity:** original file, sheet/header choice and original row number retained alongside the unmodified timestamp text. Every drop, conversion or aggregate must have a traceable source-row map.
- **Schema:** complete ordered columns, sensor/actuator roles, metadata and label exclusion, units and missing-value markers. Exact strings remain preserved even if a separate normalized schema is used.
- **Time:** an explicit parser and date order; calendar anchors that distinguish day/month from month/day; AM/PM and fractional precision where present; duplicate/out-of-order handling; observed intervals; gap/episode identifiers; and confirmed timezone or an explicit unknown-naive designation. Never infer day/month convention from only ambiguous dates or from computer locale.
- **Labels:** observed raw tokens, validated mapping to normal/attack/unknown, annotation-file hash, event IDs and interval inclusivity. Reject unknown tokens rather than silently declaring them normal. Record attack overlap and label/annotation disagreement without tuning the model on them.
- **Processed coverage:** startup exclusions, removed rows/columns, gap-safe downsampling, incomplete tails, window endpoints and warm-up exclusions. Keep pointwise, aggregate-window and event labels distinct; do not silently call window-any labels pointwise ground truth.
- **Information boundaries:** chronological development/calibration/test roles and fitted-transform provenance. Inspection of label semantics and event alignment is a data-integrity task; held-out attack outcomes must not be used to choose preprocessing, thresholds or preferred model variants.

Synthetic fixtures can later test malformed labels, ambiguous dates, two-row headers, feature/label alignment, gaps and median-versus-any aggregation without any private dataset. Those tests would validate software behavior, not establish that the actual received release contains those conditions.

## Disposition

| Candidate | Dataset compatibility decision |
|---|---|
| CAROTS | **Conditional first baseline.** Concrete file expectations are available, but source hashes, timestamps and actual schemas remain pending. Its loader requires explicit alignment, missingness, cache and coverage decisions before execution. |
| IT-DT | **Unresolved release and implementation.** Study the method; any independent implementation on our authorized common release must disclose our data/algorithm choices and retain its preprint status. |
| Ensemble | **Numerical hold.** Exact release, day splits, cadence and complete preprocessing need clarification. Its described mechanisms remain relevant background regardless of whether its numerical protocol becomes reproducible. |

New detail relative to earlier audit notes: WADI's missingness filter also inspects metadata/label cells; SWaT's first-row issue must be described as a first-**parsed**-row difference until the actual header is known; file-order splitting is not timestamp validation; and a residual/window sample count must not be relabelled as elapsed seconds. Earlier release/hash unknowns remain unknown. No earlier raw-data measurements were contradicted because no such measurements exist.
